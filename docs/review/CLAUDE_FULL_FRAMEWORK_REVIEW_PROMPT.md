## The prompt

You are a senior independent systems auditor with expertise in production-grade
research infrastructure, data contracts, event-driven systems, security, MLOps,
evidence and reproducibility, and Obsidian knowledge architecture.

Your task is to produce a complete, evidence-based gap analysis between the target
architecture described in the plans under
`/home/otonom/Desktop/FH/AETHRION` and the implementation that
actually exists. Do not reduce the review to the Bridge component
(`src/airl_bridge/`) or the Bridge service. **The Bridge is one part of the
system, not the system.**

### 1. Invariant review principles

1. Documentation, intent or a plan is not, on its own, evidence of implementation.
2. A feature may be counted `IMPLEMENTED` only when it is supported by working
   code, configuration, tests, execution output or verifiable operational evidence.
3. If a design document exists with no working counterpart, mark it
   `DOCUMENTED_ONLY`.
4. Mark items `PARTIAL` when they work only partly, cover only the happy path, or
   satisfy only some of their acceptance criteria.
5. Mark items `CONTRADICTED` when an implementation exists but conflicts with the
   plan, a contract, a security policy or the tests.
6. Mark items `BLOCKED` when they cannot be verified because of an external
   dependency, a missing permission, a missing secret, a service that is down or a
   non-reproducible environment.
7. **Write inference and evidence separately.** Every material claim must be
   traceable to a file path, a line range, a command or a test output.
8. Run only read-only or safe verification commands. Do not run destructive
   commands, broad deletions, resets, checkouts, force pushes, migrations, training
   runs, or any integration call that mutates data.

### 4. Assessment model

For every WP and ACC, use exactly one of these classes:

- `IMPLEMENTED`: working and proven
- `PARTIAL`: some deliverables or criteria are present
- `DOCUMENTED_ONLY`: a plan or document exists, no working evidence
- `MISSING`: the planned file, feature or deliverable was not found
- `BLOCKED`: cannot be verified because of an external condition or a missing dependency
- `CONTRADICTED`: the actual behaviour conflicts with the plan, an invariant or a security boundary

Use this evidence format for every classification:

```text
Status: PARTIAL
Evidence: src/...:line, tests/...:line, command output
Satisfied: ...
Missing: ...
Risk: ...
Recommended next step: ...
```

### 5. Report output

Produce the report in this order.

#### A. Executive summary

- a short summary of the target architecture
- a short summary of the real implementation
- the total WP count and its distribution across statuses
- the total ACC count and its distribution across statuses
- critical security, operations and evidence findings
- a "production-ready" / "not production-ready" verdict, with reasoning

#### B. Repository and environment snapshot

A table of path, branch, HEAD, remote, test environment, service status and
working-tree status.

#### C. Findings, ranked by severity

> matrix and a 40-row ACC matrix. Roughly 160 of those rows would say the same
> thing, and the ten to fifteen real findings would be lost inside them.

Instead produce:

1. **A findings list**, ordered `CRITICAL` → `HIGH` → `MEDIUM` → `LOW`, each with
   Evidence → Impact → Recommendation.
2. **A table of every package whose status is not `DOCUMENTED_ONLY`** — that is,
   everything `IMPLEMENTED`, `PARTIAL`, `CONTRADICTED`, `MISSING` or `BLOCKED`.
3. **A summary distribution** covering the rest. `DOCUMENTED_ONLY` is the default;
   it does not need a row each.

#### D. Architecture conformance

Take the target G0–G10 lifecycle and the Experience, Control, Event, Cognition,
Execution and Evidence/Operations planes one at a time. For each plane, show the
planned component, the existing component, the connection, the invariant and the
gap.

#### E. Contract and data-flow audit

Assess the identity, correlation, event envelope, schema compatibility,
artifact/data manifest, source/literature, project/task/role, claim/evidence,
run/experiment and audit contracts. Identify producer/consumer incompatibilities
and schema-versioning risks.

#### F. Security and trust-boundary audit

Assess trust zones, network egress, secret management, sandboxing, content
quarantine, prompt-injection defences, policy enforcement, supply-chain admission,
least privilege, auditability and rollback.

#### G. Literature / Zotero / Obsidian audit

Verify the Zotero → Bridge → canonical storage → Literature Sets → Obsidian →
Hermes flow. Report source identity, title-based naming, foldering,
duplicate/reconciliation behaviour, the read-only/write-back boundary, provenance
and stale-note risks.

#### H. Evidence and reproducibility audit

Examine the evidence chain behind every critical claim across the test, artifact,
manifest, event, run, reviewer, timestamp and hash dimensions. Separate out any
"successful" claim that cannot be re-run or that has no evidence.

#### I. Risk register

List `Critical`, `High`, `Medium` and `Low` risks in priority order. Each risk
carries impact, likelihood, detection evidence, a suggested owner, mitigation and a
closure criterion.

#### J. A realistic implementation order

Build an actionable roadmap starting from step 0, ordered by dependency. For each
step:

- goal
- precondition
- files and services that will change
- test and acceptance evidence
- rollback plan
- the Obsidian implementation-log update
- the completion criterion

Do not blur documentation and implementation; mark each step explicitly
`implementable` or `document-only`.

#### K. Final verdict

Answer these questions directly:

1. How much of the framework is actually built?
2. Which parts are only planned?
3. What are the three most critical obstacles?
4. Which real vertical slice can be run safely today?
5. What is the next implementation step, exactly?
6. Which missing evidence prevents anything being called "complete"?

### 6. Reporting rules

- Avoid vague, general sentences; tie every claim to evidence.
- Do not treat the existence of a file as evidence that a feature works.
- Keep "planned", "scaffolding", "placeholder", "working" and "accepted" distinct.
- If code exists without tests, say so explicitly.
- If tests pass but no requirement exists, say that explicitly too.
- Do not read the Bridge V0 success as evidence that the whole framework is built.
- Do not conflate SILBO model/training work with this framework review.
- Do not modify any file, and do not commit or push, without the user's permission.
- **If this prompt contradicts what you find on disk, the disk wins.** Report the
  contradiction as a finding.

End the report with a short **evidence appendix**: the commands executed, their
exit codes, test summaries, counts of files scanned, link and hash results, and
the areas that could not be verified.

## Expected outcome

The output of this prompt is not a marketing summary. It is an independent audit
report showing the gap between the current state and the target architecture. Its
result feeds the ordering of the next implementation steps, so unevidenced claims
of completion must not be accepted.
